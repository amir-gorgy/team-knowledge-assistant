Knowledge Assistant Pipeline

A Markdown file is split into chunks, each chunk becomes 768 numbers, and those go into one Postgres table. A question goes through the same model, and the chunks whose numbers are closest come back first. Everything below is what the code does today, using real data from your database.

Ingest: run once per set of docs (scripts/ingest.py) Query: run on every question (scripts/search.py, MCP tools) Shared by both: same model, same table

Both rows have to use the same embedding model. Vectors from different models can't be compared, which is why each row also stores embedding_model.

Ingest

What happens to a new .md file

Worked example: Query Parameters - FastAPI.md, followed through every step.

  1. Find the files

    scripts/ingest.py · main()
    • The path you pass is either a single .md file or a folder.
    • For a folder it takes *.md at the top level only, sorted by name. Files in subfolders are not picked up.
    • Each file is read as UTF-8. The path, exactly as you typed it, becomes the chunk's source, which is used for citations.

  2. Split by headings

    Ingest/chunking.py · split_by_headings()
    • Every # to ###### heading starts a new section. The section is the heading line plus everything up to the next heading.
    • A running list of headings by level becomes the heading_path. For example, after ## Optional parameters under # Query Parameters, the path is Query Parameters > Optional parameters. Links, HTML tags, * and backticks are stripped from the path.
    • A # line inside a ``` code block is a comment, so it doesn't count as a heading.
    • Sections with a heading but no text are dropped, but their heading still appears in the paths below them.
    • Text before the first heading becomes a chunk with an empty path (skip_preamble is off by default).
    Example: this file → 8 chunks
    heading_pathchars
    (empty: text before the first heading)35
    Query Parameters > AI coding agents1,275

    Query Parameters > Query parameter type conversion1,232

    The first two rows are leftovers from the website the docs were converted from (site navigation and an "AI coding agents" banner). They're stored and searched like real content.

  3. Split long sections

    Ingest/chunking.py · split_large()
    • Sections of 2,500 characters or less (max_chars) are kept as they are.
    • Longer sections are cut into paragraphs at blank lines and packed into pieces of up to 2,500 characters. A code block is never cut, even if it's longer than that on its own.
    • Text with no blank lines is cut at line breaks instead, and a single line longer than 2,500 characters is cut into 2,500-character slices.
    • Overlap: each new piece starts with the last whole sentences of the previous piece, up to 250 characters (10%). Code is never repeated.
    • Every piece keeps the section's source and heading_path, so it can still be cited.

    250under 200 chars

  4. Embed

    Ingest/embedding.py · embed_documents()
    • Each chunk's text gets the prefix search_document: . The nomic model was trained with these prefixes, and retrieval gets worse without them.
    • Chunks are sent 32 at a time to POST http://localhost:1234/v1/embeddings (LM Studio). The URL, model and key come from EMBEDDING_* in .env.
    • Each chunk comes back as a list of 768 numbers. The code puts them back in input order and stops if any vector isn't 768 long.
    Example: "Optional parameters" (599 chars) →
    [0.0271, 0.0488, −0.1557, −0.0458, 0.0658, … 763 more]

    No single number means anything by itself. What matters is the direction of the whole list, and chunks about similar things point in similar directions.

  5. Store

    Ingest/store.py · insert_chunks() · db/init.sql
    • Each chunk becomes one row in chunks: id, source, heading_path, content, embedding_model, embedding vector(768), created_at.
    • With --reset, the whole table is emptied first. Without it, new rows are added to what's already there, so running the same file twice stores it twice.
    • At the end the script prints the table's row count. It should match the chunk count.
    Example row
    id 1033 · source data/sample-docs-md/Query Parameters - FastAPI.md
heading_path {Query Parameters, Optional parameters}
content "## Optional parameters  The same way, you can declare optional query parameters…"
embedding_model text-embedding-nomic-embed-text-v1.5 · embedding [0.0271, 0.0488, …]
Query

How a question finds chunks

Used by scripts/search.py and the MCP tool search_docs.

  1. Embed the question

    Ingest/embedding.py · embed_query()
    • The same model embeds the question, but with the prefix search_query: . That prefix tells the model this is a question looking for documents.
    "search_query: how do I declare an optional query parameter?"  →  768 numbers

  2. Compare against every row

    Ingest/store.py · search()
    • Postgres runs embedding <=> query, pgvector's cosine distance, for each row, then sorts by it and keeps the top k.
    • There's no vector index yet, so it checks all 1,535 rows every time. That makes the results exact, and at this size it takes milliseconds.

  3. Return the hits

    Hit(source, heading_path, content, distance)
    • Each hit carries its file, heading path, full text and distance. The code doesn't drop any hit for being too far away. It always returns k results, even if none of them are relevant.

Reading the score: lower is closer

Cosine distance runs from 0 (same meaning) through 1 (unrelated) to 2 (opposite). These are the actual top 3 for two of today's test queries.

Answers the question Related, but not the answer Wrong match (frontend 404 page)

Distance ranks the chunks within one query, but it isn't a fixed measure of correctness. In the 404 query, the wrong #1 and the right #2 are 0.004 apart, and the 0.30 cut-off would throw away the chunk with the actual HTTPException code (0.308).

Copilot

The commit check: /doc-impact

The same search, driven by a diff instead of a question.

  1. Copilot reads the commit

    .github/prompts/doc-impact.prompt.md
    • In agent mode, Copilot runs git show <sha> (or HEAD) and keeps the commit message and the diff.

  2. One search per changed file

    mcp_server.py · find_docs_for_diff()
    • The diff is split at each diff --git a/<path> line. Each file's query is the commit message, File: <path> and that file's changes, cut to 2,000 characters.
    • Each file's query is embedded and searched separately, keeping the top 3 per file, so one large file can't crowd out the others.
    • Hits are merged by (source, content). Each merged hit keeps its smallest distance and lists which files matched it in matched_files, sorted closest first.

  3. Copilot judges and rewrites

    Copilot's own model
    • Copilot drops hits above about 0.30, decides whether each remaining chunk is wrong, incomplete or still correct, and reports Where / Why / Suggested wording.
    • Your code only finds the chunks. The judging and rewording happen in Copilot, and the 0.30 cut-off exists only as an instruction in the prompt, not in code.

Pointing it at a different project

uv run python -m team_knowledge_assistant.scripts.ingest ../other-project/docs
  • Mixes There's only one chunks table and no project column. The new docs go in next to the FastAPI docs, and every search covers both.
  • Wipes --reset empties the whole table, FastAPI docs included. Without it, re-running a folder stores every chunk again.
  • Misses Only top-level *.md files are read. docs/guides/setup.md inside that folder would be skipped.
  • Paths source is the path as you typed it (../other-project/docs/x.md), so citations show that relative path.
  • Format Only ``` fences count as code. With ~~~ or indented code, a # comment line can be read as a heading. Files must be UTF-8.
