Knowledge Assistant Pipeline

A Markdown file is split into chunks. Each chunk becomes 768 numbers plus a list of its words, and both go into one Postgres table. A question can then be searched three ways: by meaning, where the chunks whose numbers are closest come back first; by keyword, where chunks containing the question's words come back; or both at once, with the two ranked lists merged into one. Everything below is what the code does today, using real data from your database.

Ingest: run once per set of docs (scripts/ingest.py) Query: run on every question (scripts/search.py --mode vector|keyword|hybrid, MCP tools) Shared by both: same model, same table

Both rows have to use the same embedding model. Vectors from different models can't be compared, which is why each row also stores embedding_model. Keyword search doesn't use the model at all: Postgres builds each chunk's word list itself when the row is inserted.

Ingest

What happens to a new .md file

The sample docs are 131 pages of FastAPI 0.165.0's own Markdown source, built by data/fastapi-docs-to-md.py: it inlines the code examples, strips heading anchors and leaves out the API reference stubs and the release notes. Worked example: Query Parameters - FastAPI.md, followed through every step.

  1. Find the files

    scripts/ingest.py · main()
    • The path you pass is either a single .md file or a folder.
    • For a folder it takes *.md at the top level only, sorted by name. Files in subfolders are not picked up.
    • Each file is read as UTF-8. The path, exactly as you typed it, becomes the chunk's source, which is used for citations.

  2. Split by headings

    Ingest/chunking.py · split_by_headings()
    • Every # to ###### heading starts a new section. The section is the heading line plus everything up to the next heading.
    • A running list of headings by level becomes the heading_path. For example, after ## Optional parameters under # Query Parameters, the path is Query Parameters > Optional parameters. Links, HTML tags, * and backticks are stripped from the path.
    • A # line inside a ``` code block is a comment, so it doesn't count as a heading.
    • Sections with a heading but no text are dropped, but their heading still appears in the paths below them.
    • Text before the first heading becomes a chunk with an empty path (skip_preamble is off by default).
    Example: this file → 6 chunks
    heading_pathchars
    Query Parameters1,166
    Query Parameters > Defaults555
    Query Parameters > Optional parameters609
    Query Parameters > Query parameter type conversion1,248

    The first row is the page's intro, under the # Query Parameters heading itself. Tips in these docs are /// tip blocks rather than headings, so each stays in the chunk of the section it belongs to.

  3. Split long sections

    Ingest/chunking.py · split_large()
    • Sections of 2,500 characters or less (max_chars) are kept as they are.
    • Longer sections are cut into paragraphs at blank lines and packed into pieces of up to 2,500 characters. A code block is never cut, even if it's longer than that on its own.
    • Text with no blank lines is cut at line breaks instead, and a single line longer than 2,500 characters is cut into 2,500-character slices.
    • Overlap: each new piece starts with the last whole sentences of the previous piece, up to 250 characters (10%). Code is never repeated.
    • Every piece keeps the section's source and heading_path, so it can still be cited.

    All 24 chunks over 2,500 characters are a single code block with no text around it. FastAPI's docs also repeat the same example in several sections, so 29 chunks share their exact text with another chunk. The longest, at 5,499 characters, appears 8 times in OAuth2 scopes.

  4. Embed

    Ingest/embedding.py · embed_documents()
    • Each chunk's text gets the prefix search_document: . The nomic model was trained with these prefixes, and retrieval gets worse without them.
    • Chunks are sent 32 at a time to POST http://localhost:1234/v1/embeddings (LM Studio). The URL, model and key come from EMBEDDING_* in .env.
    • Each chunk comes back as a list of 768 numbers. The code puts them back in input order and stops if any vector isn't 768 long.
    Example: "Optional parameters" (609 chars) →
    [0.0228, 0.0567, −0.1582, −0.0524, 0.0684, … 763 more]

    No single number means anything by itself. What matters is the direction of the whole list, and chunks about similar things point in similar directions.

  5. Store

    Ingest/store.py · insert_chunks() · db/init.sql
    • Each chunk becomes one row in chunks: id, source, heading_path, content, embedding_model, embedding vector(768), created_at, content_tsv.
    • content_tsv is a generated column. On insert, Postgres fills it with the chunk's words, lowercased and stemmed, with stop words dropped and each word's positions kept. A GIN index maps each word to the rows that contain it. The ingest code never writes this column.
    • With --reset, the whole table is emptied first. Without it, new rows are added to what's already there, so running the same file twice stores it twice.
    • At the end the script prints the table's row count. It should match the chunk count.
    Example row
    id 870 · source data/sample-docs-md/Query Parameters - FastAPI.md

Query

How a question finds chunks

Three searches, picked with scripts/search.py --mode. Vector is the default and the only one the MCP tools use. Keyword and hybrid run from the script only, for now.

  1. Vector: embed the question

    Ingest/embedding.py · embed_query()
    • The same model embeds the question, but with the prefix search_query: . That prefix tells the model this is a question looking for documents.
    "search_query: how do I declare an optional query parameter?"  →  768 numbers

  2. Vector: compare against every row

    Ingest/store.py · vector_search()
    • Postgres runs embedding <=> query, pgvector's cosine distance, for each row, then sorts by it and keeps the top k.
    • There's no vector index yet, so it checks all 1,203 rows every time. That makes the results exact, and at this size it takes milliseconds.

  3. Keyword: match the words

    Ingest/store.py · keyword_search()
    • websearch_to_tsquery turns the question into words the same way the chunks were indexed: lowercased, stemmed, stop words dropped. No model is called.
    • content_tsv @@ query keeps only the chunks that contain every remaining word. The GIN index finds them without reading each row.
    • With match="any", which hybrid search uses, the words are joined with OR instead, so a chunk containing any one of them qualifies.
    • ts_rank scores each match, mostly by how often the words appear, and the top k come back highest first.
    "how do I declare an optional query parameter?"
  →  'declar' & 'option' & 'queri' & 'paramet'

    Because every word has to match, long questions often find nothing. The full wording of eval question q02, "My endpoint should return a 404 when the item doesn't exist", matches 0 of the 1,203 chunks.

  4. Hybrid: merge the two lists

    Ingest/store.py · hybrid_search() · reciprocal_rank_fusion()
    • Vector search and any-word keyword search each return their top 20.
    • Reciprocal rank fusion gives each chunk 1 / (60 + rank) for every list it's in, adds them up and sorts. Only positions count, so a cosine distance and a ts_rank never have to be compared.
    • A chunk in both lists beats one at the top of only one. The fused list is cut to k.
    "Handling Errors > Import HTTPException"   vector #5, keyword #9
  1/(60+5) + 1/(60+9)  =  0.0154 + 0.0145  =  0.0299   →  hybrid #2

  5. Return the hits

    Hit · KeywordHit · HybridHit
    • Vector hits carry a distance, where lower is closer. The code doesn't drop any hit for being too far away, so it always returns k results, even if none of them are relevant.
    • Keyword hits carry a rank, where higher is better. They can come back as fewer than k, or none at all.
    • Hybrid hits carry the fused score, where higher is better (at most 0.033, first in both lists), plus their place in each list, vector_rank and keyword_rank.
    • All three carry the file and heading path for citing, plus the full chunk text.

Reading the vector score: lower is closer

Cosine distance runs from 0 (same meaning) through 1 (unrelated) to 2 (opposite). These are the actual vector top 3 for two test queries.

Keyword's top 3 are sections of Bigger Applications that each quote the same router code, responses={404: {"description": "Not found"}}. Copilot

The commit check: /doc-impact

The same search, driven by a diff instead of a question.

  1. Copilot reads the commit

    .github/prompts/doc-impact.prompt.md
    • In agent mode, Copilot runs git show <sha> (or HEAD) and keeps the commit message and the diff.

  2. One search per changed file

    mcp_server.py · find_docs_for_diff()
    • The diff is split at each diff --git a/<path> line. Each file's query is the commit message, File: <path> and that file's changes, cut to 2,000 characters.
    • Each file's query is embedded and searched separately, keeping the top 3 per file, so one large file can't crowd out the others.
    • Hits are merged by (source, content). Each merged hit keeps its smallest distance and lists which files matched it in matched_files, sorted closest first.

  3. Copilot judges and rewrites

    Copilot's own model
    • Copilot drops hits above about 0.30, decides whether each remaining chunk is wrong, incomplete or still correct, and reports Where / Why / Suggested wording.
    • Your code only finds the chunks. The judging and rewording happen in Copilot, and the 0.30 cut-off exists only as an instruction in the prompt, not in code.

Pointing it at a different project

uv run python -m team_knowledge_assistant.scripts.ingest ../other-project/docs
  • Mixes There's only one chunks table and no project column. The new docs go in next to the FastAPI docs, and every search covers both.
  • Wipes --reset empties the whole table, FastAPI docs included. Without it, re-running a folder stores every chunk again.
  • Misses Only top-level *.md files are read. docs/guides/setup.md inside that folder would be skipped.
  • Paths source is the path as you typed it (../other-project/docs/x.md), so citations show that relative path.
  • Format Only ``` fences count as code. With ~~~ or indented code, a # comment line can be read as a heading. Files must be UTF-8.
